# Проверка обновлений Tablo

Это проверка установленной сборки в `ichinya/tablo`, выполняемая воркером. Она не
меняет файлы, не запускает `git pull`, перезапуск или деплой. Страницы читают только
сохранённый результат; авторизованная открытая панель получает тот же баннер в
обычном HTML снимке `/dashboard/state` без изменения JSON конверта или его лимита.

## Метаданные установленной сборки

Передайте одинаковые значения веб-процессу и воркеру:

```dotenv
TABLO_BUILD_REPOSITORY=ichinya/tablo
TABLO_BUILD_BRANCH=main
TABLO_BUILD_SHA=<полный 40-символьный SHA установленного артефакта>
```

SHA должен описывать именно установленные файлы. Получите его из доверенного
процесса сборки/поставки, пока исходники артефакта доступны. Для локальной сборки
из чистого checkout это `git rev-parse HEAD`; сборка с локальными изменениями не
имеет соответствующего точного commit SHA. Не берите SHA удалённой ветки после
установки и не используйте его как подмену отсутствующих метаданных. Проверка
никогда не читает `.git` и не выводит установленный SHA из удалённого HEAD.

Dockerfile принимает эти значения как build arguments и сохраняет их в образе;
`compose.yaml` передаёт одноимённые значения из окружения/.env обоим сервисам при
сборке. `.git` в образе не требуется. Для архива сохраните значения поставки в
`.env` рядом с приложением или в окружении обоих процессов. При обновлении
артефакта обновите метаданные и перезапустите оба процесса.

Отсутствующие/некорректные метаданные дают «Нет данных» без запросов GitHub.
Поддерживается только официальный репозиторий `ichinya/tablo`; выбранная ветка
может отличаться от `main` и задаётся метаданными поставки.

## Периодичность и состояния

В настройках администратора можно отключить проверку или задать интервал от 1 до
525600 минут. По умолчанию — 360 минут (6 часов), отсчитываемых от завершения
проверки. Воркер проверяет отдельное расписание после каждого сайта и во время
ожидания с точностью до 5 секунд, даже если сайтов нет или их интервал больше
6 часов. Долгий проход не откладывает проверку до окончания всех сайтов.
Текущую синхронную проверку сайта он не прерывает; остановка проверяется между
сетевыми запросами.

Сначала ветка разрешается в неизменяемый SHA `L`. Сравнение установленного `I`
с `L` различает актуальную сборку, отставание, собственную сборку впереди ветки,
разошедшуюся историю и недоступные коммиты. При изменении наблюдаемого SHA
проверяется также переход предыдущего `P` к `L`. Обнаруженное переписывание
истории имеет отдельное состояние до обновления метаданных/совпадения сборки и
ветки. Оно не превращается в обычное уведомление при следующей проверке того же
SHA. Недоступный `P` сохраняется для следующей проверки вместо потери истории.

Только доказанное отставание показывает «В ветке &lt;branch&gt; доступны новые
коммиты. Обновите Tablo» и число коммитов. Баннер содержит короткие SHA, время
последнего успешного наблюдения и фиксированную ссылку сравнения. Он не хранится
в одноразовом session notice и не исчезает от просмотра страницы.

Запросы анонимные, без использования сохранённых токенов сайтов. Один запуск
ограничен тремя запросами и общим бюджетом 24 секунды, использует существующие
правила GitHub и сохранённые cooldown. Перекрытие предотвращает короткая
транзакционная claim с 60-секундной арендой; результат принимается только при
совпадении claim, ревизии настроек и отпечатка метаданных сборки.

Сбой сохраняет прежнее успешное наблюдение и помечает его устаревшим. Повторные
попытки — через 5, 30 и 120 минут, затем с обычным интервалом; меньший настроенный
интервал ограничивает эти задержки. Подтверждённый GitHub cooldown может отложить
повтор дольше. Ошибки этой проверки не останавливают мониторинг сайтов. Новая
сборка/ветка сбрасывает привязку старого результата; отключение немедленно
аннулирует незавершённую claim.

## Ручное обновление и схема данных

1. Просмотрите сравнение изменений и инструкции нужной версии.
2. Остановите веб-процесс и воркер, сделайте согласованную резервную копию базы и
   внешнего ключа токенов, сохранив настройки.
3. Установите выбранный артефакт/пересоберите образ, передайте его точные
   метаданные. Для серверной базы выполните явную команду миграции, прежде чем
   открывать писателей; обычный вход не мигрирует серверный каталог.
4. Запустите веб-процесс и воркер с одинаковыми метаданными и проверьте сохранённое
   состояние. При совпадении SHA обычный баннер обновления исчезнет.

SQLite мигрирует атомарно с 10 на 11, добавляя только singleton `self_update`.
MySQL 8.4/MariaDB 11.4 используют явную журналируемую миграцию с 9/10 на 11:
расширяют metadata CHECK допустимой версии одним ALTER, добавляют недостающие
таблицы и публикуют версию после полного допуска схемы. Прерванный DDL остаётся
`migrating`; повтор той же миграции проверяет фактическую форму перед продолжением.
Прежние строки, шифротексты, пароли и счётчики сохраняются. Writer-роли нужен
доступ к новой таблице из `deploy/server-grants.sql.example`. API reader и
публичные DTO не получают нового состояния. Формат offline transfer теперь
содержит 16 таблиц данных и логическую версию 11 с прежними ресурсными лимитами.

Штатная остановка освобождает текущий claim без изменения последнего успеха,
счётчика ошибок или срока следующей попытки; перезапуск сразу продолжает уже
наступившую проверку. Только подтверждённые ошибки GitHub/HTTP изолируются как
недоступность проверки. Ошибки общей БД, ключа и неожиданные ошибки выполнения
прерывают воркер до продолжения внешних проверок сайтов.
