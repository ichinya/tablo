# Incidents from accepted observations

Schema6 enables **prospective tracking**. Migration creates empty incident and checkpoint tables; it never reads current health values or replays pre-existing history. Old history remains readable through the existing history interface and never seeds an incident/checkpoint on migration or page reads. The first newly accepted history row after installation is the first possible observation. Existing identities/checkpoints are never rebuilt or reset.

Only the current guarded row accepted by private `SiteRepository::persistCheck` can transition an incident. Network work has ended before its single owned transaction. Current result, actual AUTOINCREMENT history identity, incident/checkpoint and relevant worker credit commit or roll back together. A stale/disabled/configuration/credential mismatch returns before projection validation. No public import, replay or reset interface exists.

- First Offline opens at its observed UTC time; its history ID is the stable incident ID. First Online/Unknown opens nothing. Repeated Offline preserves opening time, finite health reason and HTTP status.
- Same-epoch Online closes once. Unknown marks uncertainty and never recovers. Missing/paused checks produce no observations. Paused, stale and changed-current-revision qualifiers are read overlays; they invent no recovery or edit time.
- The first accepted row in a new configuration revision interrupts the prior incident without recovery. New Offline can open a fresh incident; the epoch time watermark resets. Actual revision changes and credential invalidation are inherited, including disable/enable ABA and shared credential rotation.
- History IDs order accepted observations even within one second. Equal-time Online closes, but the interval is unknown at that precision. An older same-epoch row advances the checkpoint and marks uncertainty/clock regression; it cannot recover a newer Offline. Positive intervals describe time between observations, never uninterrupted real downtime. Ongoing/interrupted/clock-invalid intervals remain unknown.
- Retention prunes history only. Incidents/checkpoints have site FK CASCADE and no FK to expiring history. Gaps in retained history or IDs across sites provide no outage evidence. Site deletion removes its projections and stale checks cannot resurrect them; other sites remain.

Authenticated GET `/incidents` reads bounded pages: default50, limit1..100, optional positive existing `site_id`, strict canonical cursor at most256 bytes, DESC opening ID with LIMIT+1 and a fixed first-page maximum-ID ceiling excluding later openings. Missing/deleted filtered sites return404, invalid/coerced/array/oversized query values422. Reads do no upstream work, projection rebuild, history replay or database mutation on an installed current schema. Retention/deletion/recovery may change later pages; there is no cross-request snapshot or total-count promise.

The page shows escaped current names, first observed Offline UTC, actual recovery or not observed, status/uncertainty/pause/staleness/configuration/clock qualifiers, and immutable finite opening health reason/status. It stores/displays no URL, credential/HMAC identity, token/cipher/key, raw error, response body/header or version payload in the incident projection. No alerts, uptime metrics, charts or public API are added.

The partial unique index enforces one unresolved incident per site and serves the live lookup. `(site_id,id)` serves filtered descending pages and site cascade; global pages use the integer primary key. Schema upgrade is additive within the existing guarded migration. Operational rollback uses an operator-owned consistent database/key backup; never lower user_version or rebuild stable incident IDs.
